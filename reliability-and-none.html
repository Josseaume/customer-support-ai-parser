The Noise
Trap / Fixed

How the simplest possible email broke a parser that reads five languages flawlessly — and the fix that closed it.

01
The symptom

Five languages pass. “Hello, test.” crashes.

Running the full 13-email batch, the parser extracted the right order ID, sentiment and urgency from French, Spanish, Hebrew, Mandarin and Russian — every one correct. Then it failed on the shortest email in the set.

The culprit was 04_noise_irrelevant.eml — body: “Hello, test.” One of the assessment’s three named traps (the Noise Trap). It came back not as a clean result but as a row error:

Observed — batch run 04_noise_irrelevant.eml → Could not extract valid data after 2 attempts:
SyntaxError: Expected ':' after property name in JSON at position 20

The model nailed Mandarin. It choked on “Hello, test.”

The instinct was “the model is bad at some languages.” The data said the opposite — so the first job was to find what actually broke.

02
Diagnosis

Not the language — the JSON

The failure was never about meaning. It was a malformed-JSON problem, and two compounding causes turned a rare glitch into a guaranteed row error.

  • 01
    The free tier emits broken JSON — even with structured outputs

    Probing gpt-oss-120b:free directly, roughly 1 response in 10 came back malformed — a stray backslash, a truncated key, trailing } } } } — even with response_format: json_schema, strict: true. The free endpoint routes across providers that don’t all honour the constraint.

  • 02
    The retry didn’t actually retry

    The original code retried twice — both at temperature: 0. A deterministic model fed the same input produces the same broken output twice. So a single bad roll failed both attempts and became a row error. The retry was there, but it had no second chance to give.

Crucially, the app never crashed — per-email isolation turned the failure into one clean row error, exactly as designed. But it was an avoidable error, and it landed on one of the named traps.

03
The fix

A retry that actually retries

Three changes in lib/extract.ts, each addressing one link in the chain — and Zod stays the final guarantee.

  • 01
    Structured outputs from the schema

    response_format is now a json_schema derived from the Zod schema via z.toJSONSchema() — one source of truth. Strictly enforced on paid models, best-effort on the free tier.

  • 02
    Jittered retry

    Up to three attempts. The first is temperature: 0 for accuracy; retries add a small jitter (0.4) so a one-off malformed roll is not reproduced identically. The retry finally has a real second chance.

  • 03
    Zod is still the gate

    Every response is parsed against EmailExtractionSchema. Anything malformed or off-shape throws here and triggers the next attempt; only valid, correctly-typed data ever reaches the dashboard.

Before → After // before response_format: json_object  ·  retry 2× @ temp 0 (identical)
// after   response_format: json_schema (from Zod)  ·  retry 3× @ temp 0 → 0.4 jitter
04
A new value

Saying “None” out loud

A noise email isn’t really Neutral / Low — it has no sentiment and needs no reply. So sentiment and urgency gained a fourth value, None, for anything with nothing to act on: noise, empty bodies, auto-bounces, bare “thanks”.

The free model initially resisted it — told only a rule, it kept labelling “Hello, test.” as Neutral / Low. Two few-shot examples in the prompt fixed that: it now emits None / None on noise and Positive / None on positive feedback, reliably.

That raised a fair question — would a different word classify better than “None”? So we ran an A/B: None vs N/A, zero-shot and few-shot, across traps and control emails.

ConditionClassification correctJSON errorsReal misclassifications
None · few-shot10 / 10 valid20
None · zero-shot9 / 9 valid30
N/A · few-shot8 / 9 valid21 over-trigger
N/A · zero-shot10 / 10 valid20

The label was never the problem. JSON reliability was.

Both words classify equally well; almost every “failure” was a JSON error, not a wrong label — and N/A even over-triggered once, tagging a casual “just checking in” as N/A instead of Low. Verdict: keep None. The effort belongs on reliability, which is exactly where it went.

06
Model choice

Does this mean go paid? No.

With the retry net in place, the free model passes cleanly. Paid becomes a deployment decision — for privacy and latency — not a rescue. It stays a one-line OPENROUTER_MODEL swap (see ADR-001).
